# FIKA 咖啡点单系统

基于 Java 17 + Spring Boot 3.2.0 + Vue 3 的连锁咖啡店点单系统（前后端分离）。覆盖**用户端点单**（多店菜单、规格定制、收藏、购物袋、优惠券、凑单、下单支付、堂食落座、会员积分、售后反馈）与**商家端经营**（入驻、工作台看板、订单处理、菜单管理、座位管理、店铺设置）两大场景，后端为 DDD 多模块架构，提供 RESTful API。

## 技术栈

| 端 | 技术 |
|---|---|
| 后端 | Java 17 · Spring Boot 3.2.0 · MyBatis-Plus · MySQL 8.0 · Redis（可选 profile 缓存）· Actuator · ZXing（落座二维码）· Maven 多模块 |
| 前端 | Vue 3 · TypeScript · Vite · Pinia · Element Plus · vue-router（商家端） |

## 系统架构

### 后端模块

```
coffee-order-system-pro_back
├── coffee-common/               # 通用能力：Result 统一响应、ServiceException、全局异常处理器
├── coffee-module-auth-biz/      # 认证：用户注册/登录/忘记密码/重置密码/游客会话/店铺偏好
├── coffee-module-member-biz/    # 会员中心：消费/等级/积分只读数据（旧会员中心）
├── coffee-module-membership-biz # 会员体系：会员卡/等级规则/权益/积分兑换/卡券包
├── coffee-module-menu-biz/      # 菜单：商品/分类/收藏/凑单标记/本地图片存储（核心业务）
├── coffee-module-order-biz/     # 订单：下单/订单号/列表/状态机/营业额统计/凑单进度
├── coffee-module-payment-biz/   # 支付：支付单/渠道策略（MOCK+微信/支付宝/银行骨架）
├── coffee-module-after-sales-biz# 售后：售后单/订单反馈
├── coffee-module-seat-biz/      # 座位：分配/二维码/落座/离座/超时释放
├── coffee-module-store-biz/     # 店铺：店铺/商家（一商一店）/经营数据
└── coffee-web/                  # 聚合入口：Controller 层 + 静态资源映射
```

每个业务模块内部按 DDD 分三层：`api`（对外 Service 接口 + DTO）/ `domain`（领域模型 + 仓储接口 + 领域服务）/ `infra`（MyBatis-Plus 持久化实现）。

### 前端结构

配套前端仓库为 `../coffee-order-system-pro_front`：

- **用户端**（无路由，App.vue 三态切换）：`auth` 登录/注册 → `main` 点单主页 → `member` 会员中心。主页流程组件：选店弹窗 → 菜单页（分类 tab）→ 商品详情弹窗（规格/定制/加料）→ 购物袋侧栏（优惠券选择 + 凑单进度条）→ 支付弹窗。
- **商家端**（vue-router，`/merchant/*`）：入驻/登录 → 工作台 → 订单管理 → 菜单管理 → 座位管理 → 店铺设置。
- **状态管理**：Pinia 双 store——`app.ts`（用户会话/游客会话/店铺偏好/购物袋/座位）与 `merchant.ts`（商家会话/店铺）。

## 一、用户端功能模块

### 1.1 游客模式与账号认证

**游客免登录点单**：首次打开页面即调用 `POST /api/guest/session` 签发游客身份 `guestId`（`g-` 前缀），后续下单、收藏、占座全部以该身份入库隔离；游客身份仅存于前端内存（刷新后重新签发）。游客数据与登录用户数据互相不可见。

**账号体系**：用户名 + 密码注册登录；支持忘记密码（申请重置令牌 → 提交新密码）；登录后返回用户 id/昵称/累计消费/会员等级，前端据此恢复会话。

**游客数据合并**：游客登录后自动把该身份下的收藏迁移到用户账号（并集去重），随后清理游客侧记录。

### 1.2 多店铺选择与偏好记忆

用户端左上角可切换店铺（仅列出营业中店铺），菜单、类目、座位、凑单推荐均按当前店隔离。**偏好记忆**：切换店铺时通过 `PUT /api/auth/user/{id}/preference` 落库；下次打开应用时 `GET` 读取并自动恢复上次店铺，无偏好时兜底选中第一家营业店铺。未选店铺时菜单为空并弹出选店引导。

### 1.3 菜单浏览与商品定制

菜单按类目 tab 展示（内置 5 个共享类目：咖啡/茶饮/甜品/简餐/冰品 + 商家自定义类目），每店可见的商品 = 全局共享品 + 该店专属品。

商品详情弹窗支持**规格定制**：

| 方式 | 说明 |
|---|---|
| 标准规格 | SMALL / MEDIUM / LARGE 三档（各档可单独定价，缺档回落基础价） |
| 定制规格 | 选择 CUSTOM 后按品类单位输入数量——咖啡/茶/冰品类按毫升（ml），甜品/简餐按克（g）；价格 = 中等款单价 × 输入量 ÷ 基准（饮料基准 300ml、餐品基准 100g），定制尺寸落库 `custom_size` |
| 加料 | 可选加料列表（如奶油、珍珠）随订单明细落库 |

### 1.4 收藏

商品卡片可收藏/取消收藏（登录用户按 userId、游客按 guestId 隔离存储，幂等）。会员中心"我的收藏"tab 展示收藏列表，可跳转回对应店铺下单。

### 1.5 购物袋与优惠券

购物袋侧栏管理已加购商品（改数量、删行），实时汇总金额。**优惠券**：会员在购物袋中选择优惠券（固定三张权益券 FIKA8 满48减8 / SWEET12 满78减12 / BEAN15 满88减15，满足门槛才生效，仅会员可用；卡券包无门槛券暂未接入下单抵扣）；游客无券。下单时按会员折扣 + 优惠券顺序计算实付。

### 1.6 凑单（满减进度条）

购物袋内置**凑单进度条**：按购物袋金额（会员折后、券前）自动计算距最近一张满减券门槛还差多少——已选券按该券门槛，未选券**卡券包未使用满减券优先**、其次固定三张权益券（游客只看固定券）。达标后进度条自动隐藏。

"去凑单"按钮弹出**凑单推荐**：列出当前店标记为凑单推荐品（`topup=1`，如小料杯、矿泉水、迷你甜品、迷你饮品，¥3-6 档）中**最低可买价 ≤ 还差金额**的商品，按最低价升序；点击以最低价档位一键加购，进度条即时刷新，可连续凑到达标。凑单标记由商家在菜单管理里维护。

### 1.7 下单与订单状态流转

购物袋确认后提交订单（支持单品与批量混合下单）。**下单即创建支付单**，订单进入**待支付**状态，响应携带支付单号自动拉起收银台；支付成功后才进入商家待处理队列（未支付订单对商家不可见、不计入商家统计，但用户本人可见并可取消）。

每笔订单生成**详细订单号**（`YYMMDD-商家6位-类目3位-店铺当日顺序3位`，如 `260807-687257-001-034`）作为存档凭证，取餐号 = 订单自增 id（`#34`），店内叫号用。批量订单为 1 单 + N 明细模型（明细含折后单价/小计，合计 = 实付总额）。

订单状态流转：`待支付 → 待处理 → 制作中 → 已完成`；用户端在**待支付**状态可取消订单，完成后可申请售后/反馈（见 1.11）。用户订单列表按时间倒序，卡片展示订单号、商品名、实付金额、状态、预计出餐时间，点击可查看明细与详细订单号。

### 1.8 支付

下单成功后自动拉起支付弹窗（也可在待支付订单上"去支付"）。支付渠道当前为 **MOCK 模拟支付**（点确认即支付成功，订单流转待处理，开发/演示跑通全流程）；微信支付/支付宝/银行渠道为骨架占位（返回 501 未接入），按各渠道类 TODO 接入即可，无需改动支付单流程。支付单号（`PAY`+时间戳）唯一，同订单重复支付被幂等拦截；渠道回调入口已预留（幂等可重放）。

### 1.9 堂食座位

店内用餐场景支持**扫码落座**：

1. 用户端选桌：按就餐人数（1-8 人）分配空闲座位 → 展示座位号与**落座二维码**（座位编号 `店名-座位号` 编码为二维码内容）；
2. 扫码确认落座：另一设备/同一页面解析二维码 → 确认后座位变为已落座，占用者身份（userId/guestId）落库；
3. 刷新恢复：本地丢失座位状态时，按身份查询当前店已落座座位自动恢复；
4. 离座释放：离开后释放座位。

每店预置 99 桌（双人桌 70、四人桌 20、多人桌 9），分配后 **15 分钟未落座自动释放**（超时可配）。

### 1.10 会员中心与会员体系

**会员中心**（只读展示）：昵称、累计消费、累计优惠金额、会员等级与升级进度条（距下一等级差多少、百分比）、积分、固定三张权益券展示。

**会员体系**（操作能力）：

- **开卡**：首次进入自动开卡（幂等），从消费记录快照初始化等级与积分；会员卡 = 积分账本（等级/积分/累计消费/累计已兑换）。
- **等级与折扣**：REGULAR（无折扣）→ VIP（累计消费 ≥100 元，95 折）→ SVIP（≥500 元，9 折）；下单按等级折扣优惠，支付完成后按实付金额 × 等级倍率加分并重算等级。
- **积分**：每消费 1 元积 1 分（按等级倍率），取消已完成订单退款时回滚。
- **积分兑换**：积分兑换页展示可兑换项（如 1000 分换 12 元无门槛券 ×5 + 10 元无门槛券 ×4），兑换后按张拆入**卡券包**（`user_voucher`），卡券状态：未使用/已使用/已过期；卡券包的满减券会参与凑单目标计算。
- **权益列表**：按当前等级实时计算的可享权益（等级折扣 + 权益券）接口下发，前端免硬编码。

### 1.11 订单管理与售后反馈

已完成订单卡片提供两个入口：

- **售后**：申请退款/重做/换货/其他，需填写问题描述（≥4 字）。规则：仅已完成订单可申请、仅本人订单、同订单防重复提交；提交后进入待处理，售后弹窗内可查看"我的售后记录"。
- **反馈建议**：对已完成订单提交评分（1-5）+ 建议内容（≥2 字），历史反馈可在弹窗内查看。

## 二、商家端功能模块

### 2.1 注册入驻

商家账号与顾客账号完全隔离（独立表）。注册有两种模式：

- **入驻现有店铺**：选择可入驻店铺（21 家种子店中未入驻的）→ 校验用户端账号密码（沿用同一密码）→ 激活该店**预分配的占位商家记录**并绑定，商家编号（`sj-` 前缀）即登录账号；
- **开新店**：生成独立商家档案，之后通过"我的店铺"开店。

### 2.2 登录与工作台

商家编号 + 密码登录后进入工作台。工作台展示：今日营业额（仅统计已完成出餐订单）、今日订单数、待处理订单数、近 7 天每日营业额曲线、最近 5 笔订单。

### 2.3 订单管理

订单列表按店隔离（商家只能操作本店订单），状态过滤 tab：待处理 / 制作中 / 已完成 / 已取消（不含待支付订单）。

- **接单**：待处理 → 制作中，展示预计出餐时间；
- **完成**：制作中 → 已完成（此时计入营业额、会员加分）；
- **取消**：制作中 → 已取消；
- 点击订单行抽屉展示详细订单号（可复制）、商品明细、备注、取餐方式。

### 2.4 菜单管理

- 商品列表（含下架商品，展示在售状态、三档价格、凑单标记）；
- 新增商品（编码店内唯一）、编辑商品（改价/描述/上下架/**凑单标记**）；
- 上传商品图片（本地落盘，返回可访问 URL）；
- 自定义类目：创建仅本店可见的分类（图标可选）。

**写时复制机制**：编辑/下架共享商品时自动复制为该店专属副本再修改，共享记录永远只读，保证各店初始数据一致、修改互不影响。

### 2.5 座位管理

查看本店全部座位状态图（空闲/已分配/已落座，按桌型分组），展示占用者身份与分配/落座时间；已分配超时未落座的座位自动释放回空闲。

### 2.6 店铺设置

维护店铺资料（店名/地址/电话/营业时间）与营业状态（营业中/打烊）——打烊后店铺从用户端可选列表中消失。

## 三、核心业务机制

| 机制 | 说明 |
|---|---|
| 写时复制商品 | `menu_item.store_id`：0=共享商品（所有店可见），N=该店专属副本；编辑共享品自动复制，互不影响 |
| 共享类目 | `menu_category.store_id`：0=5 个内置类目，N=商家自定义类目（仅本店可见，code=`cus`+时间戳） |
| 占位商家 | 21 家种子店铺预分配占位商家记录（`sj-` 编号预生成），商家入驻 = 激活占位记录，一商一店 |
| 详细订单号 | `YYMMDD-商家6位-类目3位-店铺当日顺序3位`，唯一索引 + 并发重试 3 次防重号 |
| 订单明细分摊 | 折扣/优惠券按总额计算后按原价比例分摊到明细行（尾差归最后一行），明细合计 = 实付 |
| 营业额口径 | 今日/近 7 日营业额仅计 COMPLETED（完成出餐）；今日订单数计全部非 UNPAID |
| 未支付订单隔离 | UNPAID 订单对商家不可见、不计入任何商家统计；仅下单用户可见/可取消 |
| 本地图片存储 | 上传落盘 `{user.home}/coffee-uploads/{storeId}/`，静态映射 `/uploads/**`（生产需 nginx 代理） |
| 游客数据隔离 | 收藏/订单/座位按 userId 与 guestId 双维度隔离入库 |

## 四、快速开始

### 1. 数据库准备

```sql
CREATE DATABASE coffee_order_pro DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

表结构以 `sql_backup/` 最新一份 mysqldump 为准。**无自动建表脚本**，新环境需导入备份或手工建表；共享商品（41 个）与共享类目（5 个）为种子数据，新环境需从现库导出导入。

已有环境升级时，按版本执行 `sql/migrations/` 中的脚本；例如售后唯一约束与卡券核销字段见 `V20260809_01_business_closure.sql`。该脚本兼容 MySQL 5.7+/8.0+ 且可重复执行；执行前先备份数据库并处理脚本注释中说明的历史重复数据。

### 2. 修改配置

编辑 `coffee-web/src/main/resources/application.yml`：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/coffee_order_pro?useSSL=false&serverTimezone=Asia/Shanghai
    username: <你的用户名>
    password: <你的密码>

coffee:
  seat:
    qr-base-url: http://<本机局域网IP>:5173   # 座位二维码内容基础地址（手机扫码可达，生产改部署域名）
```

### 3. 启动后端

```bash
mvn -pl coffee-web -am spring-boot:run    # 或 IDE 运行 coffee-web 的 CoffeeWebApplication
```

服务启动在 `http://localhost:8088`，健康检查 `GET /health`。

### 4. 启动前端

```bash
cd ../coffee-order-system-pro_front
pnpm install
pnpm dev
```

前端开发环境 Vite 代理需同时配置 `/api` 与 `/uploads`（漏配 `/uploads` 会导致商品图片 404）。

## 五、配置项一览

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `coffee.seat.qr-base-url` | http://localhost:5173 | 座位二维码内容基础地址（开发填局域网 IP，生产填域名） |
| `coffee.seat.assign-timeout-minutes` | 15 | 分配后未落座自动释放时长 |
| `coffee.seat.two-seats / four-seats / multi-seats` | 70 / 20 / 9 | 各桌型数量（每店） |

> 注：`application.yml` 中 `coffee.seat.store-name` 为历史遗留死配置（座位编号前缀实际取 `store.name`），可清理。
