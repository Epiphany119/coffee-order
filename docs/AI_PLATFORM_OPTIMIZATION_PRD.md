# FIKA AI 平台优化目标 PRD

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 产品 | FIKA 咖啡点餐系统 |
| 版本 | 1.0 |
| 目标 | 建立可审计、可恢复、可度量的 AI 业务闭环 |
| 支付 | 保留模拟支付，用于演示和联调；不宣称真实收款能力 |
| 范围 | 顾客点单 Agent、商户运营 Agent、知识库、内部服务鉴权 |

## 2. 背景与问题

当前系统已经具备顾客咨询、推荐、点单计划、订单创建、模拟支付和商户运营分析等能力，但关键状态主要依赖进程内对象，知识同步与运营动作缺少可靠恢复机制，内部服务接口缺少统一的服务身份认证。AI 输出也缺少统一的来源、版本和业务结果记录。

本次优化把 AI 当作业务流程的一部分处理：模型负责理解和表达，业务服务负责权限、数据、状态和最终执行。

## 3. 产品目标

### 3.1 业务闭环目标

顾客链路必须能够完成：

```text
自然语言咨询 → 菜单/知识检索 → 推荐或点单计划 → 用户确认
→ 创建订单 → 模拟支付 → 履约状态 → 订单查询/售后 → 结果记录
```

商户链路必须能够完成：

```text
经营数据分析 → AI 提案 → 商户确认 → 创建执行任务
→ 发券/通知 → 记录每个对象的执行结果 → 统计转化
```

### 3.2 平台目标

- 所有 AI 执行均具备 `traceId`、主体、门店、模型版本和知识版本。
- AI 不能直接写订单、支付、库存或优惠券；写操作必须经过已有业务服务和用户/商户确认。
- 计划、任务、事件和知识同步在多实例、重启和重复请求下可恢复、可幂等。
- 回答中的业务事实应能关联到知识文档、菜单数据或工具结果；没有可靠证据时明确降级。
- 内部服务使用统一的服务身份、时间戳、随机数、请求体摘要和 HMAC 签名协议。

## 4. 非目标

- 本阶段不接入真实微信、支付宝或银行卡支付。
- 本阶段不替换现有 GLM 适配器，不引入新的 Agent 框架。
- 本阶段不允许模型获得数据库直连权限或任意 SQL 能力。

## 5. 关键用户故事

### 顾客

1. 顾客询问门店菜单和促销，AI 返回带来源的回答。
2. 顾客说出偏好后，AI 生成可确认的点单计划。
3. 顾客确认后创建订单，使用模拟支付完成演示链路。
4. 顾客查询订单或发起售后时，历史会话只属于当前用户和门店。

### 商户

1. 商户请求经营分析，AI 返回指标和证据。
2. 商户确认提案后，系统生成一次性执行任务。
3. 任务失败、重启或重复投递时，不重复发券，并能继续处理未完成对象。

### 运维与审计

1. 运维能看到一次 AI 请求调用过的工具、知识版本、耗时和业务结果。
2. 内部服务拒绝没有有效签名、过期时间戳或重复 nonce 的请求。
3. 发生模型、知识库或业务服务故障时，系统能返回可解释的降级结果。

## 6. 功能需求

### P0：安全与可靠边界

- 前端 API 地址只允许配置白名单 HTTPS 域名，禁止用户通过 URL 参数把令牌发送到任意地址。
- 模拟支付必须显式标记为 `MOCK`，并在运行配置中可审计；生产配置不得误认为真实支付。
- `/internal/**` 接口必须通过内部服务鉴权，网关和网络隔离作为第二层防线。
- 内部签名覆盖 HTTP 方法、路径、时间戳、nonce、请求体 SHA-256 和服务名。
- 时间戳允许偏差默认不超过 5 分钟；nonce 在有效窗口内只能使用一次。
- 单次内部请求体默认不超过 1 MiB，防止鉴权过滤器被大请求消耗内存。
- 密钥只从环境变量或密钥管理系统读取，禁止写入代码仓库。

### P1：可恢复业务状态

- AI 计划从 JVM 内存迁移到 Redis 或数据库，支持原子领取、过期、失败和同键重放。
- 商户提案保存 `analysisId`、版本和内容摘要，执行任务支持 Outbox、重试和逐对象幂等。
- 模拟支付也使用支付交易号、回调事件号和幂等状态机，保证演示结果可审计。
- 会话主键包含主体、角色、场景和 `storeId`，跨门店复用会话必须拒绝。

### P1：知识和回答质量

- 文档、分块、Embedding 和向量索引具有版本和同步状态。
- 知识更新使用异步任务和重试，不能只记录日志后丢弃。
- 统一输出 `answer`、`claims`、`sourceIds`、`confidence`、`requiresConfirmation`。
- 用户输入和知识内容都视为不可信文本；工具权限和参数由服务端再次校验。

### P2：运营度量

- 持久化提示词版本、模型版本、知识版本、工具调用、token、延迟和结果。
- 增加 AI 计划采纳率、下单转化率、模拟支付完成率、退款率、来源覆盖率和单成功订单成本。
- 评估集覆盖点单、缺货、优惠券、支付失败、重复回调、越权、跨门店和提示词注入。
- 生产环境关闭评估接口或限制为运维身份。

## 7. 内部接口鉴权标准

采用服务到服务的 HMAC 请求签名，协议字段如下：

```text
X-Service-Name: coffee-order-service
X-Key-Id: order-service-v1
X-Timestamp: 1710000000
X-Nonce: 32 字节随机值
X-Content-SHA256: hex(body sha256)
X-Service-Signature: hex(hmac-sha256(secret, canonical-request))
```

Canonical Request：

```text
HTTP_METHOD
PATH
TIMESTAMP
NONCE
CONTENT_SHA256
SERVICE_NAME
```

服务端必须校验：服务名、密钥状态、时间窗口、nonce 唯一性、请求体摘要和常量时间签名比较。密钥支持按 `keyId` 轮换，旧密钥只在过渡窗口内有效。生产环境仍应使用内网、网络策略或 mTLS 作为纵深防御。

库存服务部署至少需要配置：

```text
COFFEE_INTERNAL_AUTH_ENABLED=true
COFFEE_INTERNAL_AUTH_REPLAY_STORE=redis
COFFEE_INTERNAL_AUTH_KEY_COFFEE_ORDER_SERVICE_V1=<至少 32 字节的随机密钥>
COFFEE_REDIS_HOST=<内网 Redis 地址>
COFFEE_REDIS_PORT=6379
```

调用方使用 `InternalRequestSigner.headers(...)` 生成请求头，并使用与请求完全一致的 JSON 字节计算摘要。密钥轮换时新增 `*-v2`，先同时部署新旧密钥，再移除旧密钥。

## 8. 验收标准

- 任意 `apiHost` 参数不能改变生产 API 目标，也不能导致令牌外发。
- 无效内部签名、过期签名、重复 nonce、错误 body 摘要均返回 `401/403`。
- 两个应用实例之间可以完成同一 AI 计划的创建和确认。
- 模拟支付重复提交和重复回调只产生一次状态变化。
- 商户任务中途失败后可以继续处理，已完成对象不会重复发放。
- 门店 A 的会话不能被门店 B 读取。
- 每条可验证业务事实都能找到来源或工具证据；无证据时返回降级回答。
- 关键 AI 请求能关联到订单、支付、任务或售后结果。

## 9. 实施顺序

1. 内部服务 HMAC 鉴权基础设施和前端 API Host 防护。
2. AI 计划、会话和模拟支付的持久化状态与幂等。
3. 商户提案执行任务和知识库 Outbox。
4. 结构化回答、来源引用和版本审计。
5. 评估集、业务指标、限流和发布门禁。

## 10. 追加实现记录（2026-09-26）

已落地 AI 接口级限流：

- 客户规划、方案确认、商家增长、经营 Agent、评测接口分别配置窗口和额度。
- Redis 作为集群共享计数器，使用固定窗口和过期时间。
- Redis 暂不可用时降级到有界本机桶，避免单节点被无限请求拖垮。
- 限流键使用已认证用户、商家、骑手或游客身份；无法识别身份时使用远端地址。
- 超限返回 HTTP 429，并返回 `Retry-After`。

配置入口：`coffee.ai.rate-limit`，生产环境建议保留 Redis 限流并通过环境变量调整额度。

知识库向量同步也已加入 Redis 持久化重试队列：

- MySQL 文档是事实源，Embedding 或 Milvus 暂时失败不会丢失待同步文档。
- 队列按文档 ID 去重，定时批量消费，失败采用指数退避，最长退避 1 小时。
- 服务重启后队列仍然存在；文档被删除或禁用时会自动清理队列项。

## 12. 阶段交付定义与完成状态

双层 Loop 的外层质量控制面设计、回放评测、修复验证、发布门禁和灰度回滚方案见 [`DUAL_LOOP_AI_APPLICATION_PRD.md`](DUAL_LOOP_AI_APPLICATION_PRD.md)。该文档是下一阶段架构 PRD，当前只代表设计和实施路线。

本项目采用“能力建设、业务闭环、运营度量、生产发布”四道门禁。P0、P1、P2 描述的是可审查的交付范围，不代表数据库、密钥和部署环境已经自动完成配置。

### 12.1 P0：安全边界与基础可靠性

**负责的问题**：防止前端越权、内部接口伪造、模型直接执行高风险写操作，以及缺少身份和门店边界。

**已完成内容**：

- 前端生产 API Host 白名单，禁止通过任意 URL 参数外发 Token。
- 用户、商家、骑手、游客四类身份隔离，Agent 会话绑定主体、角色和 `storeId`。
- `/internal/**` 使用服务名、Key ID、时间戳、Nonce、请求体 SHA-256 和 HMAC-SHA256 签名。
- 内部鉴权拒绝过期签名、重复 Nonce、错误请求体摘要、错误服务名和无效密钥。
- AI 写操作经过业务服务、权限检查和显式确认，不允许模型直接写订单、支付、库存或优惠券。
- AI 接口按身份和场景限流，超限返回 HTTP 429 和 `Retry-After`。
- 生产密钥通过环境变量注入，Token 和支付回调的开发占位密钥会被拒绝。

**交付证据**：内部鉴权代码、前端 API Host 校验、AI 限流拦截器、生产配置文件和 JDK 17 编译记录。

**剩余门禁**：生产环境必须配置真实密钥、HTTPS、Redis Replay Store、网关访问控制和服务间网络隔离；这些属于部署验收，不能只通过代码仓库证明。

### 12.2 P1：AI 业务闭环与可恢复状态

**负责的问题**：AI 结果不能只停留在内存或聊天文本中，重复请求、服务重启、回调重放和部分失败都必须可恢复。

**顾客链路**：

```text
咨询/检索 -> 推荐或点单计划 -> 用户确认 -> 幂等创建订单
-> 模拟支付 -> 支付状态变更 -> 订单履约 -> 查询/售后/审计
```

**商家链路**：

```text
经营数据 -> AI 分析 -> 带 analysisId 的提案 -> 商家确认
-> growth_agent_action -> growth_agent_outbox
-> 按顾客投递券/通知 -> 失败重试 -> 结果审计与指标统计
```

**已完成内容**：

- AI 计划持久化到 Redis，支持过期、重复确认、失败恢复和多实例共享。
- 顾客会话按身份和门店隔离，拒绝跨用户、跨角色、跨门店读取。
- 商家提案保存 `analysisId`、`proposalVersion`、`proposalHash` 和状态。
- 商家动作按目标顾客拆分 Outbox，使用唯一键防止重复投递，支持指数退避和失败后继续处理。
- 券码采用确定性编号，通知和券发放在单个顾客事务中完成。
- 模拟支付具备支付单、交易流水号、回调状态机和重复回调幂等；交易流水号冲突会被拒绝。
- 知识文档保存内容哈希、文档版本、Embedding 状态和错误信息，Embedding/Milvus 失败进入 Redis 重试队列。
- P1 数据结构集中在 `V20260926_25_ai_p1_completion.sql`。

**P1 完成定义**：同一个计划、动作、支付回调或知识文档重复提交时，不产生重复订单、重复扣款、重复发券或重复通知；服务重启后未完成任务可以继续消费。

### 12.3 P2：运营度量、版本审计与评测门禁

**负责的问题**：无法回答“哪个 Prompt、模型、知识版本产生了什么结果”，也无法量化 AI 的业务价值和成本。

**已完成内容**：

- `agent_run` 和 `agent_eval_result` 持久化 Prompt、模型、知识库和工具契约版本。
- 记录工具调用、工具耗时、结果数量、模型调用次数、输入/输出/总 Token、模型成本、降级原因和最终业务结果。
- 新增商家门店级接口 `GET /api/business-agent/metrics?storeId=&days=`。
- 指标包括运行成功率、降级率、平均延迟、计划采纳率、下单转化率、模拟支付完成率、退款率、知识来源覆盖率、评测通过率、模型总成本和单个成功订单成本。
- 生产配置默认关闭评测，可通过 `COFFEE_AI_EVALUATION_ENABLED=true` 在受控环境开启。
- P2 数据结构集中在 `V20260927_26_ai_p2_observability.sql`。

**P2 完成定义**：一次 Agent 运行可以通过 `runId` 还原身份、门店、版本、工具、Token、延迟、结果和成本；商家可以按门店和时间窗口查看核心指标；生产环境不会因为评测接口产生业务写入。

## 14. 发布验收清单

### 14.1 功能验收

- 顾客可以完成“咨询 -> 计划 -> 确认 -> 订单 -> MOCK 支付 -> 履约查询”。
- 重复确认请求只产生一个订单。
- 重复支付请求只发生一次状态变化。
- 相同支付单收到相同交易流水号的回调只返回当前状态。
- 相同支付单收到不同交易流水号的回调被拒绝。
- 商家重复执行同一动作不会重复发券或通知。
- Outbox 消费进程重启后能够继续处理 PENDING 任务。
- 知识库向量服务不可用时，MySQL 文档仍可检索，队列恢复后能够补偿同步。

### 14.2 安全验收

- 缺少 Authorization、身份类型错误、身份 ID 不匹配和门店不归属时返回 401/403。
- 修改请求体后，内部签名校验失败。
- 重复使用同一个 Nonce，第二次请求被拒绝。
- 时间戳超出窗口的请求被拒绝。
- 生产环境使用开发 Token 或支付回调密钥时应用启动失败或接口拒绝请求。
- 修改 `apiHost` 不会让生产前端把 Token 发往非白名单域名。
- AI 超出额度返回 429，且不会调用模型或写入业务状态。
- 日志、审计和错误响应不包含 API Key、Token、密码和完整支付密钥。

### 14.3 可观测性验收

- 一次请求能够关联 `traceId`、`runId`、身份、门店、Prompt 版本、模型版本和知识版本。
- 每个工具调用都有开始/结束时间、状态、耗时、结果数量和错误信息。
- 模型调用能够记录 Token、成本来源和降级原因。

### 19.3 面试官最可能质疑的问题

#### 为什么需要这么多模块？

#### AI 如何防止误下单？

> 模型不能直接写订单。模型只能生成受约束的计划，后端会执行工具白名单、参数校验、权限校验和用户确认，确认后再通过幂等业务服务创建订单。

#### 支付回调重复怎么办？

> 使用支付单号、交易流水号和状态机约束回调，重复回调只返回当前状态，不重复扣减库存或变更订单。

#### 模型失败怎么办？

> 模型调用失败会降级到规则解析或人工确认，业务写操作不会依赖模型直接完成。失败原因、版本和降级结果都会被记录。

#### 你怎么证明 AI 有效果？

需要准备：

- 评测样本数量
- 意图识别准确率
- 计划解析成功率
- 工具调用成功率

- 平均延迟和 P95

- 知识来源覆盖率

没有这些数据时，AI 部分容易被认为只是功能演示。

## 20. AI Agent 职责收敛与六项整改方案

### 20.1 架构决策：仅保留两个用户可见 Agent

- **顾客 Agent**：统一负责咨询、点单计划、订单查询、反馈/售后入口。点单仍执行“生成计划—顾客确认—服务端校验及幂等下单—模拟支付”。
- **店长 Agent**：统一负责经营分析、提案生成、店长确认、受控动作执行、Outbox 重试及审计。
- 原 `BusinessAgentOrchestrator` 的 `/ask`、`/stream` 是独立的只读问答入口，不是 Agent 间协作器；本项目没有顾客 Agent 与店长 Agent 的委派协议。该对话入口与两端能力重叠，将停止作为第三个产品 Agent。
- 知识检索、菜单读取、指标读取、审计、评测和知识管理等有用能力作为共享后端服务，按顾客/店长权限供两个 Agent 使用。仍被前端使用的管理接口和评测/审计能力保留，不因下线通用对话而整体删除。
- 前端/API 类型与测试清理无调用的通用对话功能；迁移前检索所有引用，保留知识管理、指标、评测和审计调用。

### 20.2 六项修正方案

#### 1. 知识库可见范围

给知识文档增加 `CUSTOMER_PUBLIC` / `MERCHANT_INTERNAL` 可见范围。顾客默认只能检索公开知识；店长只能维护和检索所属门店授权知识。关键词查询、Milvus 候选回查、菜单知识初始化和重试同步使用同一策略；向量检索后仍须由 MySQL 校验门店及可见范围。既有文档迁移时默认内部可见，人工审核后再公开。

**验收**：顾客读不到内部文档；顾客能读公开文档；店长不能读写其他门店文档。

#### 2. 两个 Agent 的身份和门店授权

将 scene 作为严格枚举；非法值返回 400，不再静默转成 customer。顾客链仅允许 USER/GUEST，店长链仅允许 MERCHANT，RIDER 均拒绝。每个商户请求服务端验证商户与 storeId 归属；同步及 SSE 入口用同一授权组件。

**验收**：覆盖 USER/GUEST/MERCHANT/RIDER 身份矩阵、伪造 merchantId/storeId 和非法 scene。

#### 3. 商户提案绑定服务端分析

分析完成后服务端保存规范化提案并生成 proposalId、版本、哈希和待确认状态。客户端确认仅提交 proposalId/版本，不可提交或覆盖提案正文。服务端核对商户、门店、状态、版本、哈希后条件更新；执行端从数据库读取已确认内容，经动作白名单和 Outbox 投递，重复确认不能重复执行。

**验收**：篡改内容、伪造/跨店 ID、旧版本、并发或重复确认均拒绝或幂等返回。

#### 4. 经营数据故障不得伪装成零

工具结果区分真实零值、成功值、部分成功和查询失败，携带时间范围、来源及更新时间。关键数据不可用时停止生成依赖它的建议或明确标记降级；禁止用 0/空集合吞掉数据库异常，Prompt 将缺失数据视为未知。

**验收**：模拟数据源故障后不输出基于零值的确定性经营建议。

#### 5. 顾客入口和流式阶段

Customer Supervisor 作为统一顾客入口，分流咨询、点单、查单、反馈；专用 plan/confirm API 保留为点单子流程。写操作仍须专用接口和显式确认。SSE 阶段只由真实处理回调触发；无法准确报告时只发处理中和结果。明确反馈/售后是展示入口还是实际提交。下线通用 Agent 对话入口，保留仍有调用方的管理、知识、指标、评测和审计 API。

**验收**：顾客入口职责清楚，订单未确认不能创建，SSE 不提前报告未执行阶段。

#### 6. 测试文件更新，本轮不执行测试

单元测试覆盖知识可见性、身份策略、非法 scene、提案绑定/状态机、指标故障分类、路由和 SSE 状态。集成测试覆盖顾客订单及支付幂等、知识 SQL/向量范围隔离、商户提案确认与篡改、Outbox 重试、身份/门店权限、经营数据故障降级。评测报告须明确其测试覆盖范围；通用只读评测不代表订单/支付/商户执行链通过。测试文件需更新并列出命令，本轮不运行测试，由项目负责人后续执行。

### 20.3 数据库迁移与交付要求

### 20.5 本轮实现记录与测试交接

本轮代码按上述决策收敛，产品可见 Agent 只有顾客 Agent 和店长增长 Agent。顾客侧 `CustomerSupervisorAgentOrchestrator` 是统一入口；受控点单服务是顾客 Agent 内部的业务步骤，不作为第三个对话 Agent。店长侧保留原经营分析、提案和 Outbox 执行能力。原通用对话控制器、编排器、计划解析器和通用工具注册表已删除；审计、评测、知识、指标等运维能力由独立的 `AgentOperationsController` 或两个 Agent 的授权服务承载。

本轮变更落实情况：

### 20.6 支付成功与订单状态原子更新（2026-10-02）

**问题**：支付记录先提交为 PAID，之后订单再从 UNPAID 更新为 PENDING。两个独立提交之间若服务异常退出，会出现支付单已成功、订单仍待支付。

**本轮目标**：在当前模拟支付和已启用的回调链路中，将支付状态写入与订单状态迁移纳入同一个 Spring 本地数据库事务。二者必须同时提交或同时回滚；不得返回支付成功但订单仍为 UNPAID。

**实现约束**：
- 支付应用服务在单一事务边界内执行支付单状态条件更新和订单状态条件更新。
- 支付状态更新服务使用 REQUIRED 传播，加入外层支付事务；不得使用 REQUIRES_NEW 拆分支付状态提交。
- 订单支付状态更新加入同一个事务管理器与数据源。订单从 UNPAID 到 PENDING 的条件更新失败时，整笔事务回滚，支付单状态和 transaction_no 不得单独提交。
- 同一支付单的重复支付仍由支付状态条件更新阻止；相同交易流水的重复回调保持幂等。
- 当前真实支付渠道尚未接入。未来外部渠道的资金扣款无法由本地数据库事务回滚；接入真实渠道前必须另行设计确认、补偿/退款和对账流程，不得将本地事务描述为跨支付机构原子事务。

**验收标准**：
1. 模拟支付成功时，payment.status=PAID 与 user_order.status 从 UNPAID 到 PENDING 一起提交。
2. 订单状态更新被拒绝或抛出异常时，payment 状态、transaction_no 和订单状态均保持事务前状态。
3. 并发支付只有一次状态迁移成功；重复支付或相同回调不会重复推进订单。
4. 通过事务集成测试验证“支付单写入成功、订单状态更新失败”时两表同时回滚。

**实现记录**：`PaymentServiceImpl.pay` 与 `handleCallback` 建立事务边界；`PaymentStateService` 的状态写入改为 `REQUIRED`，并与 `OrderPaymentServiceImpl.markPaid` 共用当前应用的事务管理器和数据源。订单状态迁移失败会抛出异常，支付状态及交易流水号随同一事务回滚。新增 H2 集成测试 `PaymentAtomicityIntegrationTest`，覆盖模拟支付成功、支付/回调时订单更新失败回滚，以及重复回调。**本轮未运行测试**。该原子性仅覆盖同一应用内、同一事务管理器管理的数据源；接入真实外部支付后，渠道扣款不能被本地数据库回滚，仍需独立设计渠道确认、补偿/退款和对账。

### 20.7 顾客 Agent 确认重试、方案持久化与价格复核（2026-10-02）

**问题**：确认 API 默认每次生成新的 `Idempotency-Key`；顾客第一次确认已创建订单但响应超时后，重试会被方案注册表拒绝，无法取回幂等表中保存的原订单响应。当前控制器还在查询幂等结果之前重新校验方案、商品和库存；首次订单已占库存时，同 key 重试可能先因库存不足失败。方案注册表在生产开关启用但 Redis Bean 缺失时会静默退回 JVM 内存；仓库文档记载 `request_idempotency(scope,idempotency_key)` 唯一约束，但当前仓库缺少可核对/补建该表和约束的迁移脚本。方案报价虽由服务端菜单价格生成，下单前未与方案展示价复核，菜单调价后会直接按新价下单而不要求顾客确认。

**本轮目标与实现约束**：

1. **稳定确认幂等键**：同一 `planToken` 的重复确认使用同一个 key；新方案使用不同 key。请求体指纹绑定方案令牌、门店、履约方式、配送地址和是否包含凑单项；同 key 改变这些字段返回 409。
2. **幂等优先于方案校验**：服务端先按已认证身份域、key 和确认请求指纹查询/抢占 `request_idempotency`。命中 SUCCESS 时先返回原订单响应，不再访问方案注册表、不重新检查库存，也不再次创建订单或支付单。只有首次请求进入创建流程后，才读取方案并校验商品和库存。
3. **Redis 故障关闭**：生产配置显式启用 Redis 方案注册表。开关启用但 Redis Bean 缺失时应用启动失败；Redis 读写故障时方案创建/确认返回服务不可用，严禁切换到 JVM 内存。JVM 内存实现仅供明确关闭 Redis 的开发/测试配置使用。`application-prod.yml` 当前已默认启用该开关，本轮补齐其 fail-closed 行为。
4. **补齐持久化幂等 DDL**：新增数据库迁移，创建 `request_idempotency` 表并确保 `(scope,idempotency_key)` 唯一索引存在。迁移先列出重复键预检；若已有重复记录，不自动删除或覆盖，须人工核对清理后再建唯一索引。实际数据库是否已存在该表/索引只能由项目负责人在目标环境查询确认；本轮不连接或修改数据库。
5. **价格变化要求再次确认**：方案生成时将服务端计算、实际展示给顾客的商品单价保存在服务端方案快照。确认时按门店、商品、规格重新计算菜单价；任一商品单价与快照不一致，不创建订单、不完成幂等记录，返回旧/新商品价、差额和新的报价方案令牌。前端展示变价明细并要求顾客明确接受新价；接受后以新方案令牌再次提交。新订单最终价格仍由订单服务基于数据库现价、会员规则和优惠规则计算，任何客户端/模型金额都不作为定价输入。

**验收标准**：

1. 模拟首次确认成功但响应丢失后，用原方案和相同 key 重试，即使库存已被首单占用、旧方案已过期，也返回原订单响应；订单、支付单、配送单均不重复创建。
2. 同一身份域、同一 key 修改方案/门店/履约/地址/凑单选择时返回 409；不同身份域不能读取或占用彼此幂等记录。
3. 生产 Redis Bean 缺失时启动失败；运行时 Redis 不可用时请求失败关闭，不得读写本机内存方案。
4. 菜单价变化时首个确认不创建订单，返回新报价及新方案令牌；顾客明确接受后才可创建，订单服务落库实付金额继续按数据库现价计算。
5. SQL 迁移在新库可建表和唯一约束；已有库执行前可检查重复键，重复记录不被静默丢弃。

**测试交接**：补齐后端同 key 超时重试、库存已占用仍回原响应、换 key 冲突、价格变化后二次确认、Redis 缺失/不可用失败关闭等测试，以及前端 key 稳定性和价格确认交互检查。测试由项目负责人运行；迁移脚本由项目负责人备份并检查目标数据库重复记录后手工执行。本轮不自动运行测试或数据库脚本。

## 21 下单重试、支付结果核对与生产配置边界（2026-10-04）

### 21.1 本轮审查发现

1. **普通购物车下单没有跨重试复用幂等键**：HomeView 每次提交都调用 API 默认生成新 key。若服务端已提交订单但响应丢失，顾客再次点击会以新 key 重试，后端无法把它识别为原请求，可能产生第二笔订单。
2. **支付响应丢失后前端状态可能陈旧**：支付接口已成功提交而响应超时，收银台仍保留本地 PENDING 并提示失败；再次支付会收到状态冲突，但页面没有主动重新查询支付单。
3. **生产 Redis 配置依赖部署 profile**：application.yml 默认 active profile 为 local，方案注册表默认关闭 Redis；application-prod.yml 默认启用 Redis，但环境变量可以显式关闭。若生产启动漏设 SPRING_PROFILES_ACTIVE=prod，或将 Redis 开关设为 false，方案会落到 JVM 内存，重启或多实例确认会失败。
4. **Agent 方案跨幂等键的唯一性缺少数据库最终约束**：当前 Redis claim 阻止同一方案使用不同幂等键；幂等表只对 (scope,idempotency_key) 唯一。若 Redis claim 丢失而方案记录仍存在，数据库无法独立保证一个 planToken 只创建一单。
5. **数据库迁移状态无法从代码仓库证明**：幂等服务直接读写 request_idempotency；仓库提供迁移脚本，但未发现自动迁移运行器。实际目标库是否已执行脚本、是否有唯一索引，需在数据库环境手工核实。

### 21.2 本轮编码范围与实现约束

1. 普通购物车同一请求的网络重试和页面刷新重试复用同一 Idempotency-Key。前端优先使用 Web Crypto 计算 SHA-256 指纹；不可用时使用仅用于重试匹配的确定性摘要。在当前浏览器标签页的 sessionStorage 中仅保存指纹和不透明 key，不保存订单备注等原始请求数据。购物车、门店、身份、履约方式、地址、优惠或备注变化后生成新 key；服务端返回成功后清除该 key。
2. 支付请求失败或超时时，前端按已知 paymentNo 回查支付单。查到 PAID 时按成功收尾并关闭弹窗；仍为 PENDING 时刷新页面状态并允许用户决定是否重试；查询也失败时明确显示“结果未确认”，不将其误报为确定失败。
3. 生产 profile prod 下禁止关闭 Agent 方案 Redis 注册表，避免错误配置静默退回 JVM 内存。Redis bean 缺失时启动失败；Redis 运行期读写不可用时现有逻辑保持失败关闭并返回服务不可用。部署仍须显式激活 prod profile。
4. 本轮不修改数据库脚本、不连接或操作实际数据库。
