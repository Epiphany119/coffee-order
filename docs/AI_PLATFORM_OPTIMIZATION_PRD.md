# FIKA AI 平台优化目标 PRD

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 产品 | FIKA 咖啡点餐系统 |
| 版本 | 1.0 |
| 目标 | 建立可审计、可恢复、可度量的 AI 业务闭环 |
| 支付 | 保留模拟支付，用于演示和联调；不宣称真实收款能力 |
| 范围 | 顾客点单 Agent、商户运营 Agent、知识库、内部服务鉴权 |

## 2. 背景与问题

当前系统已经具备顾客咨询、推荐、点单计划、订单创建、模拟支付和商户运营分析等能力，但关键状态主要依赖进程内对象，知识同步与运营动作缺少可靠恢复机制，内部服务接口缺少统一的服务身份认证。AI 输出也缺少统一的来源、版本和业务结果记录。

本次优化把 AI 当作业务流程的一部分处理：模型负责理解和表达，业务服务负责权限、数据、状态和最终执行。

## 3. 产品目标

### 3.1 业务闭环目标

顾客链路必须能够完成：

```text
自然语言咨询 → 菜单/知识检索 → 推荐或点单计划 → 用户确认
→ 创建订单 → 模拟支付 → 履约状态 → 订单查询/售后 → 结果记录
```

商户链路必须能够完成：

```text
经营数据分析 → AI 提案 → 商户确认 → 创建执行任务
→ 发券/通知 → 记录每个对象的执行结果 → 统计转化
```

### 3.2 平台目标

- 所有 AI 执行均具备 `traceId`、主体、门店、模型版本和知识版本。
- AI 不能直接写订单、支付、库存或优惠券；写操作必须经过已有业务服务和用户/商户确认。
- 计划、任务、事件和知识同步在多实例、重启和重复请求下可恢复、可幂等。
- 回答中的业务事实应能关联到知识文档、菜单数据或工具结果；没有可靠证据时明确降级。
- 内部服务使用统一的服务身份、时间戳、随机数、请求体摘要和 HMAC 签名协议。

## 4. 非目标

- 本阶段不接入真实微信、支付宝或银行卡支付。
- 本阶段不替换现有 GLM 适配器，不引入新的 Agent 框架。
- 本阶段不允许模型获得数据库直连权限或任意 SQL 能力。

## 5. 关键用户故事

### 顾客

1. 顾客询问门店菜单和促销，AI 返回带来源的回答。
2. 顾客说出偏好后，AI 生成可确认的点单计划。
3. 顾客确认后创建订单，使用模拟支付完成演示链路。
4. 顾客查询订单或发起售后时，历史会话只属于当前用户和门店。

### 商户

1. 商户请求经营分析，AI 返回指标和证据。
2. 商户确认提案后，系统生成一次性执行任务。
3. 任务失败、重启或重复投递时，不重复发券，并能继续处理未完成对象。

### 运维与审计

1. 运维能看到一次 AI 请求调用过的工具、知识版本、耗时和业务结果。
2. 内部服务拒绝没有有效签名、过期时间戳或重复 nonce 的请求。
3. 发生模型、知识库或业务服务故障时，系统能返回可解释的降级结果。

## 6. 功能需求

### P0：安全与可靠边界

- 前端 API 地址只允许配置白名单 HTTPS 域名，禁止用户通过 URL 参数把令牌发送到任意地址。
- 模拟支付必须显式标记为 `MOCK`，并在运行配置中可审计；生产配置不得误认为真实支付。
- `/internal/**` 接口必须通过内部服务鉴权，网关和网络隔离作为第二层防线。
- 内部签名覆盖 HTTP 方法、路径、时间戳、nonce、请求体 SHA-256 和服务名。
- 时间戳允许偏差默认不超过 5 分钟；nonce 在有效窗口内只能使用一次。
- 单次内部请求体默认不超过 1 MiB，防止鉴权过滤器被大请求消耗内存。
- 密钥只从环境变量或密钥管理系统读取，禁止写入代码仓库。

### P1：可恢复业务状态

- AI 计划从 JVM 内存迁移到 Redis 或数据库，支持原子领取、过期、失败和同键重放。
- 商户提案保存 `analysisId`、版本和内容摘要，执行任务支持 Outbox、重试和逐对象幂等。
- 模拟支付也使用支付交易号、回调事件号和幂等状态机，保证演示结果可审计。
- 会话主键包含主体、角色、场景和 `storeId`，跨门店复用会话必须拒绝。

### P1：知识和回答质量

- 文档、分块、Embedding 和向量索引具有版本和同步状态。
- 知识更新使用异步任务和重试，不能只记录日志后丢弃。
- 统一输出 `answer`、`claims`、`sourceIds`、`confidence`、`requiresConfirmation`。
- 用户输入和知识内容都视为不可信文本；工具权限和参数由服务端再次校验。

### P2：运营度量

- 持久化提示词版本、模型版本、知识版本、工具调用、token、延迟和结果。
- 增加 AI 计划采纳率、下单转化率、模拟支付完成率、退款率、来源覆盖率和单成功订单成本。
- 评估集覆盖点单、缺货、优惠券、支付失败、重复回调、越权、跨门店和提示词注入。
- 生产环境关闭评估接口或限制为运维身份。

## 7. 内部接口鉴权标准

采用服务到服务的 HMAC 请求签名，协议字段如下：

```text
X-Service-Name: coffee-order-service
X-Key-Id: order-service-v1
X-Timestamp: 1710000000
X-Nonce: 32 字节随机值
X-Content-SHA256: hex(body sha256)
X-Service-Signature: hex(hmac-sha256(secret, canonical-request))
```

Canonical Request：

```text
HTTP_METHOD
PATH
TIMESTAMP
NONCE
CONTENT_SHA256
SERVICE_NAME
```

服务端必须校验：服务名、密钥状态、时间窗口、nonce 唯一性、请求体摘要和常量时间签名比较。密钥支持按 `keyId` 轮换，旧密钥只在过渡窗口内有效。生产环境仍应使用内网、网络策略或 mTLS 作为纵深防御。

库存服务部署至少需要配置：

```text
COFFEE_INTERNAL_AUTH_ENABLED=true
COFFEE_INTERNAL_AUTH_REPLAY_STORE=redis
COFFEE_INTERNAL_AUTH_KEY_COFFEE_ORDER_SERVICE_V1=<至少 32 字节的随机密钥>
COFFEE_REDIS_HOST=<内网 Redis 地址>
COFFEE_REDIS_PORT=6379
```

调用方使用 `InternalRequestSigner.headers(...)` 生成请求头，并使用与请求完全一致的 JSON 字节计算摘要。密钥轮换时新增 `*-v2`，先同时部署新旧密钥，再移除旧密钥。

## 8. 验收标准

- 任意 `apiHost` 参数不能改变生产 API 目标，也不能导致令牌外发。
- 无效内部签名、过期签名、重复 nonce、错误 body 摘要均返回 `401/403`。
- 两个应用实例之间可以完成同一 AI 计划的创建和确认。
- 模拟支付重复提交和重复回调只产生一次状态变化。
- 商户任务中途失败后可以继续处理，已完成对象不会重复发放。
- 门店 A 的会话不能被门店 B 读取。
- 每条可验证业务事实都能找到来源或工具证据；无证据时返回降级回答。
- 关键 AI 请求能关联到订单、支付、任务或售后结果。

## 9. 实施顺序

1. 内部服务 HMAC 鉴权基础设施和前端 API Host 防护。
2. AI 计划、会话和模拟支付的持久化状态与幂等。
3. 商户提案执行任务和知识库 Outbox。
4. 结构化回答、来源引用和版本审计。
5. 评估集、业务指标、限流和发布门禁。

## 10. 追加实现记录（2026-09-26）

已落地 AI 接口级限流：

- 客户规划、方案确认、商家增长、经营 Agent、评测接口分别配置窗口和额度。
- Redis 作为集群共享计数器，使用固定窗口和过期时间。
- Redis 暂不可用时降级到有界本机桶，避免单节点被无限请求拖垮。
- 限流键使用已认证用户、商家、骑手或游客身份；无法识别身份时使用远端地址。
- 超限返回 HTTP 429，并返回 `Retry-After`。

配置入口：`coffee.ai.rate-limit`，生产环境建议保留 Redis 限流并通过环境变量调整额度。

知识库向量同步也已加入 Redis 持久化重试队列：

- MySQL 文档是事实源，Embedding 或 Milvus 暂时失败不会丢失待同步文档。
- 队列按文档 ID 去重，定时批量消费，失败采用指数退避，最长退避 1 小时。
- 服务重启后队列仍然存在；文档被删除或禁用时会自动清理队列项。
