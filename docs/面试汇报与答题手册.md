# FIKA 咖啡点单项目｜面试汇报与答题手册

> 用途：复习项目介绍和面试官何晋杰提出的问题。本文根据仓库当前代码与文档整理，问题范围为已收到的第 6–14、19–24 题。
> 核验基线：Git `4b08ab6`（2026-10-08）；本文更新：2026-11-15。仓库继续演进后，尤其是金额类型、排序实现和测试结果，应重新核对。

## 一、项目汇报（约 1 分钟）

FIKA 是面向咖啡门店的点单与经营平台。顾客端覆盖选店、菜单浏览、商品定制、下单、支付单和履约查询；商家端支持门店菜单和订单经营。项目的 AI 部分包括顾客咨询与点单 Agent，以及店长增长 Agent。

顾客点单 Agent 会把自然语言需求转成品类、商品、件数、预算、冷热偏好和排除项等结构化约束，再基于当前门店菜单召回并生成方案。用户确认后，服务端重新检查身份、商品、价格和库存，再创建订单与支付单。模型不直接写数据库，也没有未经确认就扣款的权限。

后端当前以 Java 17、Spring Boot 3 和 Maven 多模块组织，是按领域拆分的模块化单体。模块边界采用 DDD 风格，主要包括认证、菜单、订单、支付、库存、会员和 Agent 等。项目重点是完整业务链路、订单安全边界和可验证的 Agent 决策；真实支付、生产基础设施验收等仍需单独完成。

## 二、面试问题与口述回答

建议先直接回答问题，再用一个实际代码链路或设计取舍补充。第一人称内容需按自己的真实贡献调整。

### 6. “刚才是用来干嘛的？是什么架构来的？”

> 这是 FIKA 的顾客点单 Agent，用来理解顾客的自然语言需求并生成当前门店可买的商品方案。Agent 的编排层负责理解和分流，菜单、订单、支付等领域模块负责真实业务。整体后端是 Spring Boot 模块化单体，模块按领域拆分并分层；微服务拆分属于后续演进方向。

### 7–8. “项目是你自己从零做的吗？基于什么框架？你自己有想法，从零开始实现？”

> 这是我的个人项目。我从咖啡点单和门店经营场景出发，梳理需求、拆分模块并持续实现业务闭环。工程底座使用 Java 17、Spring Boot 3 和 Maven 多模块，我没有从零自研 Web 框架；我的工作重点是业务建模、接口和模块设计、核心链路实现与验证。

> 如果实际使用过开源脚手架或参考过现成模板，我会明确说明来源和使用范围，并区分脚手架能力与自己设计、实现的业务部分。

### 9. “Agent 推荐饮品，有打通购买吗？客户能通过 Agent 下单？”

> 能生成点单方案，并在顾客确认后创建正式订单和支付单。Agent 不会只凭模型输出自动完成交易：顾客先在页面确认方案，服务端再核验商品、价格、库存和身份。当前支付是模拟支付，真实微信或支付宝交易尚不能算已打通。

### 10. “Agent 怎么给系统下单？通过什么实现？”

> 点单分成方案和确认两个阶段。`POST /api/customer-agent/plan` 生成方案及 `planToken`；页面展示方案，用户确认后调用 `POST /api/customer-agent/plans/confirm`，并提交 `Idempotency-Key`。服务端从自己的方案仓库读取商品快照，核验门店和用户身份，重新计算价格并检查库存，再调用订单服务创建订单，之后创建支付单。配送单则在外卖场景下继续创建。

> `planToken` 当前有效期为 5 分钟，并绑定门店和顾客/游客身份；确认时重新检查价格和库存。启用 Redis 时使用共享存储，本地或测试配置可使用 JVM 内存方案仓库。

### 11. “Agent 是怎么调 API 的？”

> 浏览器通过 REST API 调用后端；Agent 编排层通过受控的 Java 服务接口调用菜单、订单等业务能力。模型不会自己拼接 URL、直连数据库或获得任意 API 权限。模型输出的商品编码必须来自服务端候选集，最终还要过服务端的权限、预算、价格、库存和幂等校验。

> 对多件商品或多个必需品类，当前代码由服务端确定性组合排序；模型不决定一个组合是否合规。单品流程仍保留模型辅助的意图解析/选择路径，但结果受候选集和统一校验约束。这里更准确地说是“服务端受控编排”，不要笼统说成模型拥有任意 Function Calling 权限。

### 12. “有维护饮品的功能吗？怎么维护？”

> 有。商家可以按本店维护商品分类和菜单，包括新增商品、调整规格价格、描述、图片和上下架状态。接口会检查商家对门店的归属。共享菜单商品采用写时复制：商家编辑时生成本店副本，避免一家门店改价或下架影响其他门店。

### 13. “既然 Agent 能调接口，为什么还要向量化，不直接调接口拿商品？”

> 结构化接口负责提供可信的商品、价格、在售状态和库存信息，交易必须以这些业务数据为准。向量化解决的是用户描述和商品描述之间的语义匹配，例如用户只说口味或场景。项目采用混合方式：商品名精确匹配和品类过滤、语义相似度共同补充候选；最终价格和库存仍由服务端校验。当前菜单语义向量缓存与知识文档 RAG 是两条不同路径：菜单 Embedding 缓存在 MySQL，知识文档向量检索使用 Milvus。

### 14. “可以介绍下技术栈/框架吗？”

> 后端主要是 Java 17、Spring Boot 3、Spring MVC、MyBatis-Plus 和 MySQL 8，Maven 多模块组织；前端是 Vue 3、TypeScript、Vite。AI 使用智谱聊天与 Embedding 接口，知识文档 RAG 使用 Milvus。Redis 缓存和 RocketMQ 能力按配置/profile 启用。当前主运行形态仍是模块化单体，支付演示使用 Mock。

### 19. “之前这些项目是用 AI 编程的，怎么用？”

> 我把 AI 当作结对开发工具来提高分析和实现效率，不把生成代码直接当成正确答案。一般先让 AI 阅读现有项目、梳理影响范围和备选方案，我确认设计和验收标准后，再让它协助实现、排错和补测试。我会重点人工审查权限、金额、状态机、事务、幂等和迁移脚本，再运行测试并检查差异。设计取舍和最终验收责任由我承担。

### 20. “平时日常开发是怎么做的？”

> 我通常从用户场景和验收条件开始，先梳理领域对象、状态流转和接口边界，再拆成小的端到端任务实现。每个任务补相应测试，启动本地服务验证接口和页面，根据日志定位问题，最后更新 PRD、接口或数据库文档。AI 功能会额外检查候选来源、结构化意图、硬约束、降级原因和运行轨迹。

### 21. “做出来的效果，你有什么途径去验证？”

> 我用单元测试验证规则和状态边界，用 Agent 固定样例检查路由、商品选择、必需品类、预算和确认要求，再通过本地页面和运行轨迹检查完整流程。当前仓库的 `eval/agent_cases.jsonl` 有 6 条固定样例，适合验证关键场景，不足以证明开放场景准确率。

> 按当前代码基线复跑后端 Maven 测试，87 项通过，失败、错误和跳过均为 0。受限运行环境中 Mockito 的动态自附加失败；显式加载本机 Byte Buddy agent 后通过。本次结果是后端自动化测试证据，不代表真实 MySQL、模型、支付、浏览器 E2E 或生产环境均已验收。`TEST_REPORT.md` 的 57 项结果来自 2026-09-27，是较早的历史报告；本次 87 项是 2026-11-15 对当前基线的复跑结果。更多边界见[测试报告](TEST_REPORT.md)和[Agent 评测文档](AGENT_EVALUATION.md)。

### 22. “Java 里 StringBuilder 和 StringBuffer 有什么区别？”

> 两者都是可变字符串。`StringBuilder` 不做同步，通常用于单线程拼接；`StringBuffer` 的方法带同步，适合有共享访问需求的场景，但一般有额外开销。它们都不会自动让多个方法组成的复合业务操作具备原子性。

### 23. “咖啡系统里金额字段类型怎么设计的？”

> 这部分我会如实回答项目现状：当前菜单价格、订单和支付领域对象中仍能看到 `Double`；部分下单价格复核会转换为 `BigDecimal`。数据库文档记录的菜单价格是 `DOUBLE`，支付金额是 `DECIMAL(10,2)`，Java 对象与数据库类型没有完全统一。这是已知技术债。更稳妥的设计是 Java 全链路使用 `BigDecimal`，MySQL 使用 `DECIMAL`，统一精度和舍入规则，避免用浮点数进行金额运算。

### 24. “MySQL 一般怎么优化慢查询？”

> 我会先通过慢查询日志或监控定位 SQL，再用 `EXPLAIN`/`EXPLAIN ANALYZE` 看执行计划、扫描行数和索引命中。之后检查联合索引是否匹配过滤和排序条件、是否违反最左前缀、是否对索引列做函数计算、是否读取过多字段，以及深分页、N+1 查询和不必要的关联。修改后用代表性数据复测延迟和扫描行数，同时考虑索引对写入的代价。不会只靠盲目增加索引解决问题。

## 三、核心追问速记

### Agent 点单链路

```text
顾客自然语言
  → 意图解析与约束校准
  → 当前门店菜单候选召回
  → 硬约束过滤与服务端排序
  → 方案与短时 planToken
  → 顾客确认 + Idempotency-Key
  → 复核身份、价格、库存
  → 创建订单和支付单（Mock）
```

多商品/多品类组合排序是可解释的规则算法：先按点名商品和每个必需品类保留候选，再按门店/排除项/冷热/库存/预算过滤；然后用用户偏好、收藏、热销、评分、语义分等信号打分，生成可行组合并按稳定规则排序，最多返回 3 个有差异的备选。硬约束不由模型权重覆盖。详见[顾客点单推荐与组合排序 PRD](CUSTOMER_ORDER_RECOMMENDATION_RANKING_PRD.md)及 `CustomerOrderBundleRanker`、`CustomerOrderRecommendationPolicy`。

### 项目现状中要守住的边界

- 项目当前主架构是模块化单体；不要把演进目标描述成已经上线的完整微服务集群。
- Agent 可生成订单方案并在用户确认后创建待支付订单；当前支付是模拟支付。
- 菜单 Embedding/MySQL 缓存和 Milvus 知识库检索职责不同；向量召回不负责交易事实。
- 当前评测样例数量有限；不要声称已经证明开放场景准确率、线上转化率或生产级 SLA。
- 金额字段存在 `Double` 与数据库 `DECIMAL`/`DOUBLE` 混用问题；谈改进时应明确承认并提出全链路迁移方案。
- “从零做”需准确区分业务构思/设计/代码与采用的框架、脚手架或 AI 辅助，不要把框架能力说成自研成果。
