# 顾客点单推荐与组合排序 PRD

> 版本：v1.0  
> 更新日期：2026-10-08  
> 范围：FIKA 顾客点单 Agent 的菜单召回、单品排序、套餐组合、备选重排与回归验收。  
> 实施原则：借鉴大规模推荐系统的分层结构，按当前门店菜单规模采用可解释、确定性、可降级的服务端算法；不把未经数据验证的模型指标或效果写成事实。

## 1. 背景与目标

用户会用自然语言同时表达商品、品类、口味、预算、温度、数量和排除项。例如“蛋糕加咖啡，预算 40”。此类请求不是简单地把所有商品排一个总榜，而是一个带业务约束的组合推荐问题。

本功能优先保证：

1. **稳定性**：同一门店菜单、库存、用户信号和请求应产生一致的排序结果；模型服务超时或不可用不影响核心推荐决策。
2. **准确性**：不可违反用户明确指定的商品、品类、件数、排除项、温度、当前门店、可售库存和预算上限。
3. **可解释性**：能够记录候选来源、排序分、总价、预算过滤、最终校验和降级原因。
4. **可评测性**：通过固定样例验证约束正确性与推荐顺序，不以“模型调用成功”代替推荐质量验收。
5. **可演进性**：积累足够的曝光、选择、加购和支付反馈后，再以离线评测和线上实验校准排序；不在数据稀疏时假装已经训练了个性化模型。

## 2. 业界架构借鉴与本项目取舍

公开的工业推荐系统资料通常将推荐拆成候选生成、精细评分和重排；YouTube 公开论文描述了候选生成模型与排序模型的分层做法，Google 的推荐资料将重排用于额外约束和多样性处理。Netflix 对外介绍也提到会综合用户互动、商品信息和使用场景，并利用反馈改进推荐。

FIKA 借鉴这套**架构分工**，不照搬大厂的训练规模或神经网络：门店菜单有限，显式品类、实时价格、库存和用户点名必须由业务代码保证。LLM 负责自然语言意图解析与推荐说明；商品候选与最终组合由服务端可重复的算法决定。

## 3. 端到端流程

~~~mermaid
flowchart LR
  A[自然语言请求] --> B[解析结构化意图]
  B --> C[多路召回: 点名 / MySQL品类 / RAG]
  C --> D[按必需品类保留候选]
  D --> E[硬约束过滤: 门店 / 可售 / 排除 / 温度]
  E --> F[单品加权评分与稳定排序]
  F --> G[生成预算内可行组合]
  G --> H[组合级排序]
  H --> I[多样性重排, 最多3套]
  I --> J[服务端复核库存、价格和意图]
  J --> K[签发 planToken, LLM生成说明]
~~~

上述步骤中，意图解析、RAG 和语言生成可以调用模型；D 至 J 中的业务规则必须由服务端执行。任何外部数据或模型返回的商品码都只能引用服务端白名单候选。

## 4. 功能需求与规则

### 4.1 意图结构

将请求解析为结构化字段：

- `requiredCategories`：必需品类集合，例如 `dessert`、`coffee`。
- `explicitProductNames`：用户明确点名的商品或商品类型，例如“芝士蛋糕”“蛋糕”。
- `itemCount`：实际下单件数；“推荐三款”属于展示数量，不自动变成购买件数。
- `budget`：组合总价上限。
- `excludedCategories` / `excludedProducts`：排除项。
- `temperature`、`preferenceTags`、`pricePreference`：冷热、口味和价格偏好。

解析器失败时使用规则解析。模型返回的字段必须与原始文本核对，不能凭提示词示例给用户增加预算、商品或排除条件。所有必需品类都必须进入召回与最终组合校验。

### 4.2 候选生成与品类保障

候选来源按职责合并去重：

1. **精确点名**：优先召回与用户商品词匹配的菜单项。
2. **结构化品类**：针对每个必需品类分别召回当前门店的可售商品，不能只按全局 Top N 截断，避免某一品类占满候选列表。
3. **语义补充**：RAG 可补充表达相近的商品，但不能替代显式品类、门店或库存约束。

候选集按商品 code 去重；保留显式点名命中，并为每个必需品类保留独立候选配额。当前实现参数为：每个必需品类最多 10 个候选、每条点名最多 12 个候选，再以全局排序结果补充最多 16 个通用候选。组合搜索使用最多 50,000 个搜索状态作为延迟保护；达到上限时按稳定顺序返回已发现的最佳可行组合。

若某个必需品类没有当前门店的有效可售候选，则不得用其他品类替代；推荐应失败并说明缺少可行组合。

品类标签存在包含关系时允许同一件商品覆盖多个等价/重叠要求，例如“drink”和“coffee”可由一杯咖啡同时满足；但甜点和咖啡这样的不相交品类不能互相替代。最终件数仍严格按用户要求计算。

### 4.3 硬约束过滤

下列规则是准入条件，不参与加权打分：

- 商品必须属于请求门店的当前有效菜单，且 `available=true`。
- 用户明确点名的商品词必须在最终方案中得到满足。
- 最终组合覆盖全部 `requiredCategories`；件数严格等于 `itemCount`。
- 任一排除商品或品类均不能进入组合。
- 冷热要求与商品属性一致。
- 有明确规格时，按用户点名规格的报价搜索预算内组合；未指定规格时按小规格搜索，并沿用现有方案规格策略。展示方案还必须用实际选择规格重新计价并再次校验。
- 搜索时使用库存数量快照限制同一商品的重复件数；签发方案前仍按聚合数量重新检查库存，以应对并发售卖。
- 不可行时不得静默放宽约束，也不得用 LLM 生成未在候选集中的商品。

“预算 40”解释为总价不高于 40 元，不要求凑满 40 元。用户明确指定大杯/大份时，必须按该规格的实际价格校验。

### 4.4 单品排序

硬约束过滤后，使用可解释的单品加权分。当前规则基线如下：

| 信号 | 当前分值 |
|---|---:|
| 用户收藏商品 | +36 |
| 收藏品类 | +15 |
| 门店热销 | +13 |
| 平均评分不低于 4.2 | +10 |
| 原始请求明确提及该商品 | +120 |
| 口味/场景标签 | 按 `CustomerOrderIntentCatalog` 规则累计 |
| RAG 语义分 | `round(max(0, similarity) × 40)` |
| 命中任一必需品类 | +18 |
| 冷热偏好 | 命中 +20，冲突 -18；硬过滤仍优先 |

价格偏好（便宜、中档、精品/有排面、最贵）使用当前门店实际价格生成商品偏好序位，并在同品类候选中作为排序主信号。没有价格偏好时，综合分降序排列。最终同分以商品 ID、code、名称稳定打破平局。

以上分值是可解释的规则基线，不表示训练得出的权重。新增或调整权重必须增加对应离线样例，并比较排序回归结果。

### 4.5 组合生成与组合排序

只对已通过硬约束过滤的候选生成组合。组合候选使用有界搜索，不依赖 LLM 反复试错。

组合基础分：

```text
bundleScore = Σ itemScore(product)
```

排序顺序：

1. 有明确价格偏好时，先比较组合内商品偏好序位之和（升序，越小越优）。
2. 再比较组合基础分（降序）。
3. 同分时优先总价较低的组合，避免没有理由地把用户预算花满。
4. 再按排序后的商品 code 签名升序，保证结果确定。

所有方案先满足全部必需品类和商品词，再比较分数。对没有历史依据的商品对不虚构“搭配协同分”。在积累足够的共同购买数据后，才评估使用去流行度校正的商品共现/关联分；该分只能参与排序，不能覆盖任何硬约束。

首选方案会按上述确定性顺序扫描有界搜索产生的可行组合，逐个复核实际规格价格、库存和方案签发条件；某个高分组合在实时复核时失败，不会阻止后续可行组合成为首选。最多 3 套的 MMR 重排只负责生成备选。

### 4.6 备选方案多样性重排

最多返回 3 套方案。第 1 套固定为组合排序第一名；后续方案使用 MMR 风格重排，在组合相关度和与已选方案的商品重合率之间折中：

```text
relevance = 按组合排序归一化到 [0, 1]
similarity = 当前组合与已选组合的商品多重集 Jaccard 相似度
diversityScore = 0.80 × relevance - 0.20 × max(similarity)
```

每套备选仍须重新通过全部硬约束、实时价格、库存和 planToken 校验。相同组合不得重复返回。备选多样性不能降低首选方案的相关度排序。

### 4.7 LLM 职责与故障处理

- LLM 可解析自然语言、补充推荐说明；不拥有组合准入权。
- 多商品/多品类方案不调用 LLM 决定最终商品组合，避免同一输入因采样、模型升级或供应商波动出现不同套餐。
- 单品请求保留已实现的意图解析和候选排序流程；模型生成文案失败时返回服务端模板说明。
- RAG/Embedding 超时、限流或 Milvus 故障时，语义分置零或缺失；MySQL 结构化召回和规则排序仍可完整运行。
- 检索、排序、预算或库存校验异常不得转换成 SSE JSON 序列化错误；通过既有统一错误响应返回。

## 5. 数据与反馈演进

### 当前阶段

使用菜单属性、用户收藏、门店销量、反馈评分、显式口味标签和实时语义分。当前菜单数据规模较小，固定规则更易排查，且不依赖训练数据。

### 后续阶段（需要真实数据后）

记录推荐曝光、候选位置、点击/选中、加购、确认下单、支付和取消等事件，并标记模型/规则版本。采用时间切分的离线样本评估排序，再以灰度/A/B 验证线上收益。累计足量数据后，可以评估 LambdaMART/LightGBM Ranker 或商品共现模型；未经评测不得替换确定性硬约束。

## 6. 可观测性

每次计划至少能关联到运行轨迹或诊断日志中的：

- 规范化意图与解析来源；
- 每个必需品类的候选数及召回来源（exact / MySQL / RAG）；
- 候选商品 code、单品排序分和价格偏好序位；
- 搜索状态数、可行组合数、候选组合分、排序顺序及多样性重合率；
- 预算、品类、数量、库存校验结果及不可行原因；
- 最终规则版本、LLM 版本（仅解析/文案）和降级状态。

日志不得记录认证凭证、支付信息或未脱敏个人数据。

## 7. 验收标准

### 正确性门禁

- 固定回归集内的品类、点名商品、件数、排除项和预算违规率为 **0**。
- “蛋糕加咖啡”候选集同时包含甜点与咖啡；组合必须各含至少一件，绝不返回两个甜点替代。
- 缺少任一必需品类时，返回无可行组合，不调用模型伪造替代商品。
- 超预算组合不进入首选或备选；规格变化后按实际报价再次校验。
- 多件同商品按总数量校验库存；库存不足方案不能签发 planToken。
- 同输入与同数据快照重复运行，候选顺序、组合顺序和 tie-break 结果一致。
- `embedding` 返回空、429 或超时，结构化召回与硬约束仍通过。

### 质量指标

- `category_coverage@1`：首选方案覆盖全部必需品类的比例，目标 100%。
- `feasible_bundle_recall@3`：固定真值可行组合出现在前三方案的比例。
- `top1_accept_rate`、加购率、确认下单率和支付率：上线采集后按版本观察，当前不预设虚构目标值。
- 搜索状态上限触发率、推荐耗时、Embedding 降级率和无解原因分布。

### 必测样例

1. `蛋糕加咖啡，预算40`：候选按品类分别召回；只接受预算内且满足两类的组合。
2. `芝士蛋糕加咖啡`：必须包含芝士蛋糕和咖啡，不可改成其他蛋糕。
3. `两杯咖啡，预算40`：数量准确；同商品重复数量不超过库存快照，签发前再按聚合库存校验。
4. `不要甜点，只要咖啡`：排除项优先于偏好和 RAG 分。
5. 仅有甜点、缺少咖啡：明确无可行方案，不能降级为两件甜点。
6. 同分、重复运行、候选输入顺序打乱：最终排序稳定。
7. Embedding 429、RAG 空结果：MySQL 与规则路径仍返回可行结果。
