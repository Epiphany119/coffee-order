## 1. 产品概述

### 1.1 产品背景

传统咖啡点单系统通常只覆盖商品维护和简单下单，顾客、门店、订单、支付、配送、会员和售后之间缺少完整闭环，容易出现以下问题：

- 顾客需要反复选择门店、商品和规格，复购效率低。
- 堂食、自取和外卖的履约规则不同，却容易被混在同一条简单订单流程中。
- 未支付订单、库存、支付回调、卡券和积分之间缺少一致性保护。
- 连锁门店共享菜单后仍需要独立调整商品、图片、价格和分类。
- 商家只能看到订单列表，难以结合经营数据制定可执行的增长动作。
- 大模型如果直接修改订单或数据库，会带来误下单、越权和重复执行风险。

### 1.2 产品定位

FIKA 是面向连锁咖啡门店的全链路点单与经营平台，覆盖：

1. 顾客选店、浏览菜单、商品定制、购物袋、支付、取餐和售后。
2. 游客快速下单，以及会员账号、邮箱、密码、会员权益和订单管理。
3. 商家入驻、菜单和图片管理、订单制作、座位管理、售后处理和经营看板。
4. 配送员独立身份、外卖抢单、配送状态流转、配送业绩和隐私联系框架。
5. 顾客点单 Agent、统一只读 Business Agent 和店长增长 Agent。

产品的核心不是把聊天机器人贴在 CRUD 页面上，而是把 Agent 放入“结构化方案 → 人工确认 → 正式业务链路 → 幂等与审计”的可控流程中。

| 目标 | 当前落地方式 | 当前状态 |
|---|---|---|

| 支持多种履约方式 | 到店自取、堂食座位、外卖地址与配送状态机 | 已实现 |
| 保证订单关键数据正确 | 服务端计价、库存预扣、支付单、订单状态机、幂等键和 Outbox | 已实现 |

## 2. 用户角色与权限

### 2.1 角色定义

| 角色 | 核心目标 | 已实现能力 |
|---|---|---|
| 游客 | 不注册也能快速浏览和点单 | 游客会话、选店、菜单、收藏、购物袋、到店自取/堂食、订单查询与取消 |
| 顾客会员 | 复购、获得会员权益并管理账号 | 用户名/账号号码/邮箱登录，邮箱注册与绑定，密码设置，订单、会员、积分、卡券、售后 |
| 门店商家 | 维护门店并完成订单履约 | 商家注册登录、入驻店铺、菜单和图片、订单、座位、售后、设置、经营看板 |
| 配送员 | 接单并完成外卖配送 | 独立账号、资料、待抢订单、CAS 抢单、取餐/配送/送达、业绩看板 |
| Agent | 辅助顾客或商家完成决策 | 只读检索、结构化方案、人工确认、正式接口执行、运行轨迹 |
| 平台运营 | 管理全平台规则和数据 | 当前不是独立前台角色，相关能力作为后续规划 |

### 2.2 权限原则

1. 顾客、商家、游客和配送员使用相互隔离的身份凭证，不能跨角色调用接口。
2. 顾客只能读取或修改自己的资料、邮箱、地址、订单、收藏、会员和售后。
3. 商家只能查看和操作自己门店的菜单、订单、座位和经营数据。
4. 配送员只能查看可抢配送单和自己已接单的配送单，顾客手机号通过隐私中介处理。
5. Agent 不拥有数据库连接，也不能直接执行下单、扣款、发券、改库存等核心写操作。
6. 所有关键资源在服务端再次校验归属，前端显示或参数不能作为授权依据。

## 3. 功能需求

### 3.1 顾客身份与账号安全

| 编号 | 需求 | 规则与验收 | 状态 |
|---|---|---|---|
| F-AUTH-01 | 普通注册和登录 | 用户名唯一；密码至少 6 位且包含字母和数字；登录成功签发访问令牌 | 已实现 |
| F-AUTH-02 | 多标识登录 | 登录框可输入用户名、系统账号号码或已绑定邮箱；字段仍兼容提交为 username | 已实现 |
| F-AUTH-03 | 系统账号号码 | 内部自增 id 保留不变；对外账号为 fika + 10 位数字；历史用户由迁移按 id 回填，例如 id=1 为 fika0000000001；新用户使用随机后缀 | 已实现 |
| F-AUTH-04 | 邮箱注册 | 邮箱验证成功后创建新用户；用户名由用户填写；账号号码由系统生成，不在邮箱注册界面要求用户填写 | 已实现 |
| F-AUTH-05 | 邮箱验证码登录 | 只有已绑定邮箱可以使用 LOGIN 验证码登录；验证码成功后一次性失效 | 已实现 |
| F-AUTH-06 | 多邮箱绑定 | 一个用户最多绑定 3 个邮箱；一个邮箱只能绑定一个用户；输入框失焦时检查占用，后端仍需二次校验 | 已实现 |
| F-AUTH-07 | 邮箱验证码可靠性 | 验证码哈希双写 Redis 和 MySQL；Redis 丢失或不可用时以 MySQL 兜底；使用、过期或错误次数耗尽后清理临时记录 | 已实现 |
| F-AUTH-08 | 发送频率限制 | 同一邮箱默认 60 秒只能发送一次；10 分钟内成功申请第 6 次时进入 10 分钟冷却 | 已实现 |
| F-AUTH-09 | 设置和修改密码 | 用户在个人中心设置密码或修改密码；新密码和确认密码必须一致；原密码或已绑定邮箱验证码至少通过一种身份校验 | 已实现 |
| F-AUTH-10 | 密码操作后重新登录 | 设置/修改密码成功后当前令牌不续签，前端退出当前登录态，用户使用新密码重新登录 | 已实现 |
| F-AUTH-11 | 解绑安全 | 用户中心单个邮箱解绑先弹确认窗口，再调用接口；服务端校验当前用户身份和邮箱归属 | 已实现 |
| F-AUTH-12 | 个人资料 | 昵称、电话、生日、微信号、QQ 号、其他信息和头像可维护；可选字段允许清空 | 已实现 |

邮箱验证码用途分为 REGISTER、LOGIN、BIND，并相互隔离。默认验证码有效期 5 分钟，最多校验 5 次。验证码本身不是长期业务数据，过期即无效。

### 3.5 商家端

1. 商家可以注册、登录、申请或绑定可入驻店铺，并维护个人资料、头像和经营许可证。
2. 商家只能查看自己店铺的订单；待支付订单不进入商家队列和经营统计。
3. 商家可接单、开始制作、完成制作；外卖订单完成制作后自动发布配送任务。
4. 商家可以维护商品、商品图片、共享/专属分类、价格、规格、上下架和凑单标记。
5. 商家可以查看座位状态、管理门店设置、查看订单/营业额/履约等经营数据。
6. 商家可以处理售后单，并查看店长增长 Agent 的建议、执行状态和审计记录。

### 3.6 配送员端

1. 配送员使用独立 RIDER 令牌，与顾客和商家令牌隔离。
2. 只有主订单已支付且商家完成制作后，配送单才进入 OPEN 待抢状态。
3. 抢单使用数据库条件更新，同一配送单只能有一个配送员成功抢到。
4. 配送状态为 OPEN → CLAIMED → PICKED_UP → DELIVERING → DELIVERED；配送员可以释放未取餐的配送单。
5. 配送员看板展示配送单量和订单金额，不把订单金额冒充骑手收入。
6. 顾客和配送员联系功能当前只生成 5 分钟有效的 relayId，不暴露真实手机号，也不发起真实通话。

## 4. 核心业务流程

### 4.1 普通点单流程

~~~mermaid
flowchart LR
  A[游客会话或会员登录] --> B[选择营业门店]
  B --> C[浏览菜单/搜索/推荐]
  C --> D[定制规格与加料]
  D --> E[购物袋/优惠券/凑单]
  E --> F{履约方式}
  F -->|堂食| G[分配或扫码座位]
  F -->|自取| H[确认取餐]
  F -->|外卖| I[选择本人地址]
  G --> J[创建 UNPAID 订单]
  H --> J
  I --> J
  J --> K[预扣库存并创建支付单]
  K --> L{支付}
  L -->|失败/未支付| M[顾客可取消并释放库存]
  L -->|成功| N[进入商家队列]
  N --> O[商家接单/制作]
  O --> P{履约}
  P -->|堂食/自取| Q[完成订单]
  P -->|外卖| R[发布配送单]
  R --> S[骑手抢单/配送/送达]
  Q --> T[积分/反馈/售后]
  S --> T
~~~

关键规则：

- 订单创建时状态为 UNPAID，只有支付成功后才进入商家队列。
- 价格、库存、优惠和身份均由服务端校验。
- 同一用户或游客重复提交同一 Idempotency-Key 不会重复创建订单。
- DELIVERY 只能由登录顾客发起，游客只能使用到店自取或堂食。

### 4.2 顾客点单 Agent 流程

~~~mermaid
sequenceDiagram
  participant U as 顾客
  participant A as Customer Order Agent
  participant T as 受控工具
  participant O as 正式订单链路
  participant P as 支付/配送

  U->>A: 自然语言描述口味、温度、预算或搭配
  A->>T: 读取当前店铺菜单、偏好、热度和反馈
  T-->>A: 返回白名单数据和来源信号
  A-->>U: 商品方案、理由、估算价格和 planToken
  U->>A: 人工确认方案和履约方式
  A->>O: 校验 planToken、身份、门店和幂等键
  O->>O: 服务端重新计价、扣库存、创建订单和支付单
  A->>P: DELIVERY 时创建配送单
  O-->>U: orderNo、paymentNo、deliveryOrderId
~~~

产品约束：

1. Agent 只生成当前店铺菜单中的受控商品方案，不接受浏览器自行修改商品、价格或数量。
2. planToken 默认 5 分钟有效，并绑定身份、门店和原始方案。
3. 确认操作必须人工触发；服务端再次做身份、门店、商品、库存、价格和地址校验。
4. 外卖确认必须传当前登录用户自己的 deliveryAddressId；前端已设置默认地址时自动优先使用默认地址。
5. Agent 确认最终走正式订单/支付链路，返回 paymentNo 后由前端打开支付窗口。

### 4.4 店长增长 Agent 流程

1. 店长提出经营问题，例如“最近复购下降，但今天待制作订单很多，应该怎么做？”。
2. Agent 只读取订单、营业额、履约队列、秒杀库存和知识库等允许的数据。
3. Agent 返回经营信号、证据、建议动作和执行计划。
4. 店长确认后才创建待执行方案。
5. 服务端使用状态条件更新和幂等保护执行通知或发券动作。
6. 方案、工具调用、执行状态、影响用户数和失败原因写入审计记录。

## 5. Agent 产品与安全设计

### 5.1 Agent 类型

| Agent | 输入 | 只读能力 | 可执行动作 | 当前状态 |
|---|---|---|---|---|
| 顾客点单 Agent | 顾客自然语言需求 | 菜单、收藏、热度、反馈和规格价格查询 | 经顾客确认后创建正式订单和支付单；外卖创建配送单 | 已实现 |
| 统一 Business Agent | 顾客/商家场景问题 | 场景白名单工具、知识库和运行数据 | 当前只返回建议，不直接写核心业务 | 已实现 |
| 店长增长 Agent | 经营问题和增长目标 | 订单、营业额、履约、秒杀和知识库 | 仅允许 NOTIFY_MEMBERS、CREATE_VOUCHERS 等受控动作，必须店长确认 | 已实现 |

### 5.2 结构化计划

Agent 输出至少包含：

- **scene**：customer 或 merchant。
- **intent**：用户想完成的业务目标。
- **steps**：工具名称、受限参数和调用目的。
- **signals**：来源、值和是否实际使用。
- **requiresConfirmation**：是否必须人工确认。
- **planToken/runId**：方案确认令牌和运行追踪编号。
- **fallback**：模型、向量库或外部服务不可用时的降级说明。

### 5.3 工具白名单

- 工具按场景注册，参数由服务端定义和校验。
- 顾客 Agent 只允许读取当前店铺菜单和用户身份范围内的偏好数据。
- 商家 Agent 只允许读取当前商家所属店铺的数据。
- 工具返回结果应携带来源、返回条数、状态和耗时。
- 任何写操作必须进入已有应用服务，不能由模型生成 SQL 或直接操作数据库。

### 5.4 模型、RAG 与降级

1. 当前 AI 路由使用智谱 GLM，模型和 API Key 通过环境变量或 local profile 注入。
2. 知识文档原文和权限存 MySQL，向量存 Milvus；查询时先向量召回，再按 MySQL 文档权限回查原文。
3. Milvus、Embedding、GLM 或网络异常时，Agent 降级为 MySQL 关键词检索或受控规则方案。
4. 降级时必须向前端返回可理解的降级原因，不应伪造模型分析结果。
5. Agent 评测使用 eval/agent_cases.jsonl，重点关注工具选择、门店隔离、来源引用、工具成功率、P95 延迟、模型成本和重复执行数。

| 身份 | coffee_user | 顾客内部身份、用户名、账号号码、密码哈希、会员摘要 |
| 身份 | coffee_user_email | 多邮箱绑定关系，一个邮箱唯一归属一个用户 |
| 身份 | guest | 游客会话和游客身份 |
| 身份 | merchant / delivery_rider | 商家和配送员独立身份 |
| 门店 | store | 店铺、营业状态、商家绑定和基础资料 |
| 菜单 | menu_category / menu_item | 分类、商品、规格、图片、上下架和凑单 |
| 交易 | user_order / order_item | 订单主表和多商品明细 |
| 支付 | payment | 支付单、渠道、金额、状态和回调流水 |

| 会员 | member_card / member_points / user_voucher / coupon | 等级、积分、兑换和优惠 |
| 服务 | after_sale / feedback / user_notification | 售后、反馈和站内通知 |

| 可靠性 | inventory_stock / flash_sale_claim | 库存预扣和秒杀资格 |
| 认证 | email_verification_code / email_verification_rate_limit / password_reset_token | 验证码、限流和密码重置令牌 |

### 6.2 关键一致性规则

1. **账号号码与内部 id 分离**：coffee_user.id 继续作为内部主键和关联键；account_no 是对外展示的唯一账号号码。
2. **邮箱唯一性**：coffee_user_email.email 建立唯一约束；绑定前应用校验，落库时由数据库唯一索引兜底。
3. **订单商品快照**：order_item 保存商品名、数量、价格和 image_url；历史订单不依赖当前 menu_item 的图片。
4. **地址快照**：配送单复制下单时的收货人、电话、地址和备注，顾客后续编辑地址不影响历史配送单。
5. **订单幂等**：同一业务身份和 Idempotency-Key 只能关联一个结果；请求指纹不同或并发处理中返回冲突。
6. **支付幂等**：一个订单最多关联一条有效支付单；重复回调不会重复推进订单状态。
7. **库存一致性**：预扣和释放均以条件更新保护；取消与秒杀资格过期按业务唯一键幂等处理。
8. **权益正确性**：订单完成/送达才入账积分和消费；取消已完成订单时执行相应回滚。
9. **事件可靠性**：订单领域事件先与业务数据同事务写入 Outbox，再由调度器发布和补偿。
10. **数据隔离**：所有用户、游客、商家、店铺、配送员和 Agent 运行数据均按身份或门店限制访问。

## 7. 技术方案

### 7.1 当前架构

~~~mermaid
flowchart TB
  C[Vue 3 顾客端] --> W[coffee-web Spring MVC]
  M[Vue 3 商家端] --> W
  R[Vue 3 配送员端] --> W
  W --> AUTH[认证与访问控制]
  W --> MENU[菜单/分类]
  W --> ORDER[订单/库存]
  W --> PAY[支付]
  W --> MEMBER[会员/营销]
  W --> STORE[门店/座位]
  W --> DELIVERY[外卖配送]
  W --> AGENT[Agent/RAG]
  AUTH --> DB[(MySQL 8)]
  MENU --> DB
  ORDER --> DB
  PAY --> DB
  MEMBER --> DB
  STORE --> DB
  DELIVERY --> DB
  AGENT --> DB
  W -.可选缓存.-> REDIS[(Redis)]
  AGENT -.可选向量检索.-> MILVUS[(Milvus)]
  AGENT -.智谱模型.-> GLM[GLM API]
  W -.WebSocket/SSE.-> C
~~~

当前系统是 Java 17 + Spring Boot 3 的模块化单体：

- coffee-web 负责 HTTP 控制器、身份拦截、配置和应用装配。
- coffee-module-*-biz 按 auth、menu、order、payment、membership、seat、store、delivery、after-sales、customer-agent 等领域拆分。
- 每个领域模块按 api、domain、infra 分层，模块之间通过接口协作。
- coffee-gateway、coffee-order-service 等目录保留了向微服务演进的边界，但本地演示默认启动 coffee-web。

### 7.2 技术栈

| 层 | 技术 | 当前用途 |
|---|---|---|
| 前端 | Vue 3、TypeScript、Vite、Pinia、Vue Router、Element Plus | 顾客、商家和配送员页面 |
| 后端 | Java 17、Spring Boot 3.2、Spring MVC | Web API 和应用编排 |
| 数据访问 | MyBatis-Plus、MySQL 8、JDBC | 业务表、事务和唯一约束 |
| 缓存 | Spring Cache；Redis profile 可选 | 菜单缓存、验证码可靠性、共享缓存扩展 |
| AI | 智谱 GLM、Embedding | Agent 意图解析、方案生成和知识向量 |
| RAG | Milvus + MySQL | 语义召回和权限回查 |
| 实时 | WebSocket、SSE | 订单通知和 Agent 流式输出 |
| 工程 | Maven 多模块、DDD 分层 | 领域边界和可拆分性 |
| 监控 | Actuator、Micrometer、Request-Id | 健康检查、指标和请求追踪 |

### 7.3 可靠性设计

- 请求入口生成或透传 X-Request-Id，便于日志关联。
- 下单必须携带 Idempotency-Key，结果持久化后可安全重试。
- 订单领域事件通过 Transactional Outbox 保存，调度器使用状态条件更新抢占、发布、失败重试和超时恢复。
- 支付回调、库存预扣、秒杀资格、积分和通知消费者均以业务键做幂等。
- 外部 AI、Milvus、Redis 不可用时，主点单流程仍可使用菜单和规则降级运行。
- 关键业务错误通过统一业务码返回，前端显示可理解的操作提示。

### 7.4 安全设计

- 密码使用 BCrypt 哈希保存，不在日志和响应中返回明文。
- 访问令牌由服务端签发并在请求拦截器校验。
- 用户、商家、游客和配送员身份不能互换。
- 手机号、配送员信息和地址按最小权限返回；配送员端隐藏顾客真实手机号和内部用户 id。
- 数据库密码、QQ 邮箱授权码、智谱 API Key、Token Secret 和支付回调密钥必须使用环境变量或 local 配置，不提交到 Git。
- 生产环境应限制 Actuator、数据库、Milvus 和邮件服务的网络访问。

## 8. 非功能需求

| 类别 | 当前要求与验收方式 |
|---|---|
| 正确性 | 订单、支付、库存、卡券和积分状态不能出现非法逆向迁移；通过单元测试和接口场景测试验证 |
| 安全性 | 越权访问返回 403/404；账号、邮箱、地址和店铺数据按身份隔离；通过接口鉴权用例验证 |
| 幂等性 | 重复下单、重复支付回调、重复抢单和重复 Agent 执行不会产生重复业务结果 |
| 可恢复性 | Outbox 失败可重试；Redis、Milvus、GLM 异常时有明确降级；启动不依赖可选中间件 |
| 可观测性 | 请求有 Request-Id；Agent 有 runId、callId、状态、耗时、返回条数和失败原因 |
| 性能 | 当前未填入未经压测的固定数字；上线前应按菜单查询、下单、支付回调、Agent 计划分别进行并发和 P95 压测 |
| 体验 | 表单校验即时反馈；密码可显示/隐藏；邮箱占用、验证码冷却、地址缺失和订单状态给出明确提示 |
| 数据迁移 | DDL 不由应用启动自动创建；所有结构变更通过可重复执行的版本 SQL 完成，并在测试库验证后再更新备份 |
| 隐私 | 地址和联系方式使用业务快照与最小字段返回；日志不记录密码、验证码明文或第三方授权码 |

## 9. 验收与演示清单

### 9.1 顾客端验收

- 游客创建会话，选择营业门店，浏览带图片的菜单。
- 添加多个商品，选择规格、加料、优惠券和凑单后创建批量订单。
- 重复点击确认下单，系统只生成一笔订单和一条支付单。
- Mock 支付成功后，订单才出现在商家待处理列表。
- 进入“我的订单”打开详情，明细每个商品显示缩略图；没有图片时显示咖啡图标。
- 执行订单图片迁移后，历史订单也能显示当前菜单图片回填结果。
- 选择堂食时可分配座位；选择外卖时只能选择当前顾客自己的地址。
- 会员完成订单或外卖送达后检查积分和消费累计。
- 已完成/已送达订单可以提交反馈或售后。

### 9.2 账号安全验收

- 普通注册后可以使用用户名、fika 账号号码和密码登录。
- 邮箱注册不需要填写系统账号号码；注册完成后账号号码由系统生成，并在个人资料中查看。
- 已绑定邮箱可以验证码登录；未绑定邮箱只能进入注册或绑定流程。
- 同一邮箱不能被第二个用户绑定；一个用户最多绑定 3 个邮箱。
- Redis 不可用时，验证码仍可由 MySQL 记录完成验证；验证码使用或过期后临时记录清除。
- 连续频繁获取验证码达到规则后进入 10 分钟冷却。
- 设置/修改密码需要二次确认；成功后退出登录，旧密码不能登录，新密码可以登录。
- 解绑邮箱必须先点击确认窗口，取消确认不会发送解绑请求。

### 9.3 Agent 验收

- 顾客输入自然语言需求，Agent 返回当前门店商品方案和推荐理由。
- Agent 方案展示 planToken，顾客确认后才创建正式订单。
- Agent 订单的最终价格以服务端结算为准，不能信任浏览器提交的估算金额。
- 顾客选择外卖且已有默认地址时，Agent 自动使用默认地址；没有地址时提示先选择收货地址。
- Agent 外卖确认后同时生成订单、支付单和配送单，不再出现“外卖不支持”的拒绝。
- GLM 或 Milvus 不可用时，Agent 返回规则/关键词降级结果，普通菜单点单仍可用。
- 店长 Agent 只能先生成建议，确认后才能创建和执行通知/发券动作。
- 重复确认店长 Agent 动作返回冲突，不重复发券或通知。
- 根据 runId 查看 Agent 运行轨迹和工具调用审计。

### 9.4 商家和配送员验收

- 商家只能查看和操作自己门店的订单，不能操作其他门店订单。
- 商家接单、制作和完成后，外卖订单自动进入待抢配送状态。
- 两个配送员同时抢一张配送单时只有一个成功。
- 配送员只能看到脱敏后的顾客信息和自己的配送单。
- 配送员完成送达后，顾客端订单状态和会员结算状态正确更新。

## 10. 当前限制与后续规划

### 10.1 当前限制

1. 主运行形态是模块化单体，同进程同库事务，尚未获得微服务独立扩缩容能力。
2. 支付目前以 Mock 渠道演示，微信、支付宝和银行真实支付需要接入渠道 SDK、验签和回调环境。
3. 配送费规则、骑手收入结算和第三方配送平台适配尚未接入。
4. 虚拟电话目前只有 relayId 中介框架，没有真实电话供应商。
5. 前端购物袋当前为内存态，刷新页面会丢失购物袋内容。
6. Agent 的准确率、延迟和成本尚未通过完整生产规模压测，不能在简历中填写未经评测集测量的数字。
7. 当前没有完整的平台运营后台和复杂租户计费体系。

### 10.2 后续规划

| 优先级 | 规划项 | 价值 |
|---|---|---|

| P1 | Redis Cluster、RocketMQ 和死信处理 | 支撑高峰削峰、跨模块事件和故障恢复 |
| P1 | 订单/库存/营销服务独立拆分 | 对热点领域独立扩容，保留当前 API 边界 |
| P1 | 完成 Agent 评测集、指标看板和 Prompt 版本管理 | 量化质量、延迟、成本和回归风险 |
| P2 | 对象存储和图片 CDN | 优化商品图片、头像和资质文件的生产存储 |
| P2 | 购物袋持久化与跨设备同步 | 改善复购和登录后购物体验 |
| P2 | 第三方虚拟号码和配送平台适配 | 支持真实配送沟通和外部运力 |
| P2 | 平台运营后台、多租户和权限中心 | 支撑更大规模门店管理 |

## 12. 本地运行与数据迁移

### 12.1 启动方式

后端默认端口 8088，前端 Vite 默认端口 5174。

~~~bash
# 项目根目录
mvn -pl coffee-web -am spring-boot:run -Dspring-boot.run.profiles=local

# 新终端
cd frontend
npm install
npm run dev
~~~

前端通过 Vite 将 /api 和 /uploads 代理到本地后端。数据库为 MySQL 8，默认库名为 coffee_order_pro。

### 12.2 必要配置

- local 环境填写数据库账号密码和 Token Secret。
- QQ 邮箱 SMTP 使用 QQ 邮箱授权码，不使用邮箱登录密码。
- 智谱配置填写 ZHIPU_API_KEY 或兼容的 ZAI_API_KEY。
- 需要共享缓存时启动 Redis 并启用 redis profile；Redis 不可用时邮箱验证码仍有 MySQL 兜底。
- 需要向量检索时启动 Milvus；Milvus 不可用时 Agent 降级为 MySQL 关键词检索。
- 所有真实凭证只能放在本地配置或环境变量，不能写入公共 application.yml 或提交版本库。

### 12.3 迁移顺序

当前项目不在应用启动时自动建表，必须先选择 coffee_order_pro 数据库，再按版本执行 sql/migrations 中的脚本。与当前功能直接相关的脚本包括：

1. V20260831_12_runtime_consistency.sql：幂等、Outbox、库存等运行时表。
2. V20260831_13_delivery_module.sql：地址、配送单和配送员基础表。
3. V20260901_15_delivery_rider_performance_contact.sql：骑手业绩和联系框架。
4. V20260901_16_profile_center.sql：三端个人资料字段。
5. V20260906_17_agent_observability.sql：Agent 运行轨迹和工具调用审计。
6. V20260906_18_email_auth.sql：邮箱验证码和限流表。
7. V20260907_19_multi_email_binding.sql：多邮箱绑定关系。
8. V20260907_20_user_account_no.sql：账号号码和历史用户修复。
9. V20260908_21_order_item_image.sql：订单明细商品图片快照和历史图片回填。

迁移脚本执行后应重新导出数据库结构备份，并在测试环境完成邮箱、下单、外卖、Agent 和订单图片验收。

### A.3 支付状态

PENDING 待支付、PROCESSING 处理中、PAID 已支付、FAILED 支付失败、CLOSED 已关闭、REFUNDED 已退款。

- NOTIFY_MEMBERS：向符合条件的会员写入站内通知。

- 顾客下单不是由 Agent 直接写库，而是由 planToken 确认后进入正式订单服务。
